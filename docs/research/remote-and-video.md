# 1. Marquee's phone remote

## 1.1 What it is, what serves it, how it pairs

- The Marquee TV app (webOS, Rust + C, repo `/data/home/Marquee`) has no phone remote of its own. Rust application under `rust-modules/`, `src/main.c` is a boot/crash shim. Source: `Marquee/AGENTS.md:6`.
- The "Marquee phone remote" is the LumaTV phone remote, inside the iPhone app. It is a native iOS app feature: the Swift package `LumaRemoteKit` (`/data/home/LumaRemoteKit`, GitHub `nphil/LumaRemoteKit`, MIT) embedded by `nphil/marquee-ios` (`/data/home/marquee-ios`). It is not a web app and not a PWA. Source: `Marquee/docs/marquee/ports.md` (iPhone, LumaTV remote); `LumaRemoteKit/README.md`; `marquee-ios/App/Remote/TVRemote.swift:1-60`.
- Decision: "LumaTV control is part of the Marquee iOS app"; no standalone remote app (the thin `LumaRemote` app was dropped); the kit stays separable ("Keep it separable", decision 7). Source: `D/research/phone-remote.md:414-423`; `Marquee/docs/marquee/ports.md` (LumaTV remote).
- The TV side is not Marquee. It is a first-party plugin `phone-remote` of the LumaTV helper (Rust): engine crate `lumaremote` (`/data/home/lumaglass/helper/remote`, no LumaTV dependencies) and plugin `helper/app/src/phone_remote/` (`mod.rs` 372 lines, `host.rs` 530 lines). The helper turns phone input into verbs on the LumaTV compositor's control socket. Source: `D/plugins/phone-remote.md:7-9,48-52`; `D/research/phone-remote.md:9-12,149-160`.
- Port and host: TCP and UDP port 18733 on the TV's private (home-network) address only, only while the plugin is on (off by default; off closes the listener and withdraws the mDNS record). Source: `D/plugins/phone-remote.md:31-35`; `helper/remote/src/lib.rs:36` (`pub const PORT: u16 = 18733`); `D/research/phone-remote.md:125-127`.
- Discovery: mDNS/Bonjour service `_lumatv-remote._tcp.local`, instance name = TV name, TXT `v=1`, `id` (8 random bytes as 16 lowercase hex), `name`, `mac` (wired MAC, 12 hex, for Wake-on-LAN), `pair` (`1` while a pairing window is open). Phone side: `NWBrowser`. Source: `D/research/phone-remote.md:198-201`; `LumaRemoteKit/Sources/LumaRemoteCore/Discovery.swift:5,86`.
- Pairing, QR: Settings > Remote & pointer > Phone remote > "Pair a phone". The window opens only after OK on the physical remote (AI gate prompt kind `pair_phone`). The TV then shows an 8-character code (`ABCD-EFGH`, alphabet 2-9 and A-Z without I and O) and a QR code of `lumaremote://pair?h=<address>&p=18733&id=<tv id>&c=<code without dash>`. Window lasts 5 minutes, takes 5 wrong codes, closes once a phone pairs; max 16 phones. Source: `D/plugins/phone-remote.md:11-16`; `D/research/phone-remote.md:131-133,200`.
- Pairing, code typed: also supported; the phone upper-cases and strips spaces and dashes and refuses characters outside the alphabet before connecting. Source: `D/research/phone-remote.md:214-215`.
- Pairing, QR on the phone: the host app registers the `lumaremote://` scheme and passes the URL to `model.open(url)`; Marquee owns the scheme and has its own QR scanner (`QRScanner.swift`, 200 lines). Source: `LumaRemoteKit/README.md` ("Adding it to an app"); `Marquee/docs/marquee/ports.md` (Pairing); `LumaRemoteKit/Sources/LumaRemoteKit/UI/QRScanner.swift`.
- Host app Info.plist needs `NSLocalNetworkUsageDescription`, `NSBonjourServices` with `_lumatv-remote._tcp`, `NSCameraUsageDescription`. Source: `LumaRemoteKit/README.md`.
- Auth: pairing key = PBKDF2-HMAC-SHA256(password = the 8 code characters upper case without dash; salt = ASCII `LumaRemote pair v1` + the TV id's 8 bytes; 131,072 iterations; 32 bytes). Handshake `Noise_NNpsk0_25519_ChaChaPoly_SHA256`, PSK = pairing key (mode 2) or the phone's key (mode 1). The TV generates a 32-byte per-phone key and sends it once inside the encrypted pairing session (`paired` message). TV keeps it in `<data>/phone-remote/devices.json` (root, 0600); the phone keeps it in the Keychain (`AfterFirstUnlockThisDeviceOnly`). Every connection does a fresh handshake. Source: `D/research/phone-remote.md:139-141,203-215,221`.
- Revocation: Settings removes one or all phones; the live session gets `revoked`. Pairings survive switching the plugin off. Source: `D/plugins/phone-remote.md:15-16`; `D/research/phone-remote.md:142-143,253`.
- Other gates: peers outside 10/8, 172.16/12, 192.168/16 are dropped; 8 failed handshakes in 60 s ignores that peer for the rest of the minute; handshake must finish within 3 s; nothing is answered before authentication. The pairing writes need header `X-Luma-Client: lumatv-ui` (else 403). Source: `D/research/phone-remote.md:125-130`; `D/plugins/phone-remote.md:28,37`.
- The phone remote cannot approve the TV's AI gate or open pairing. Source: `D/research/phone-remote.md:42-43,144-145`.
- Status: design dated 2026-11-06 says "Untested: all of it"; latency figures are inferred (target: added latency under 20 ms p95 on Wi-Fi, about 3-5 ms median). Whether the built version has been accepted on the TV: Not found in the files read. Source: `D/research/phone-remote.md:3,16,97,425`; `Marquee/docs/marquee/ports.md` (last paragraph: "to be measured").
- Marquee's iPhone host layer: `TVRemote` (enable flag, access point Mini Bar or Home Button, sheet presentation, lifecycle: `model.activate()` only while enabled and app in foreground), `TVRemoteScreen`, `TVRemoteMiniBar`, `TVRemoteButton`, `TVRemoteSettingsView`; `LumaRemoteKit` pairings and settings live in the kit's own Keychain service and settings namespace. Source: `marquee-ios/App/Remote/TVRemote.swift` (280 lines); `LumaRemoteKit/README.md` ("Pairings live in the Keychain").

## 1.2 Transport and protocol (version 1)

- Two channels on port 18733. TCP for everything ordered (keys, text, actions, lists, state), Noise-encrypted JSON frames, `TCP_NODELAY`. UDP for pointer and scroll (a lost datagram costs one sample; datagrams carry running totals). Source: `D/research/phone-remote.md:83-87`.
- No WebSocket; no HTTP. The TCP stream starts with a 6-byte preamble `4C 52 4D 54` (`LRMT`), version `01`, mode `01` (session) or `02` (pairing). Source: `D/research/phone-remote.md:205`; `helper/remote/src/wire.rs:12-13`.
- Handshake: phone sends message 1 raw (48 bytes: ephemeral key + 16-byte tag), TV answers message 2 (48 bytes) or closes without a byte. Prologue = the 6 preamble bytes. Split: first cipher phone to TV; ChaCha20-Poly1305, nonce = 4 zero bytes + 64-bit counter, empty AD. Source: `D/research/phone-remote.md:206-210`.
- Frame after handshake: u16 length (little-endian) + ciphertext (plaintext + 16-byte tag); the plaintext is one UTF-8 JSON object with string member `t`, at most 8,192 bytes. Source: `D/research/phone-remote.md:194,211-212`.
- Pairing mode messages: phone `{"t":"pair","name":"...","model":"...","app":"..."}` (name 1-40 chars); TV `{"t":"paired","device":"<16 hex>","key":"<base64 32 bytes>","tv":{"id","name","mac"}}` then close; refusal `{"t":"error","code":"bad-message"}`. Source: `D/research/phone-remote.md:219-224`.
- Session mode: the phone's first frame is `hello`; the TV answers `welcome`, then pushes `state` on change. Source: `D/research/phone-remote.md:228`.
- Phone to TV messages (`t` and members): `hello` (`name`, `model`, `app`, `kit`); `key` (`k` key name, `a` = `tap`|`hold`|`down`|`up`; tap and hold are timed on the TV: hold is 1.1 s, 2.1 s for `mute`; down/up only for arrows, `volup`, `voldown`, `chup`, `chdown`, `rew`, `ff`; `home` is tap only); `text` (`s`, 1-256 bytes UTF-8, no control chars); `edit` (`op` = `backspace` with `n` 1-256, `enter`, `tab`, `left`, `right`, `clear`, `hide`, `show`); `act` (`id` u32, `do`, args); `get` (`id`, `what` = `apps`|`channels`|`cameras`); `ping` (`n`); `bye`. Source: `D/research/phone-remote.md:232-241`; `D/plugins/phone-remote.md:39`.
- TV to phone messages: `welcome` (`v`:1, `device`, `tv`{`id`,`name`,`mac`,`accent` `#rrggbb`}, `udp`{`session` u32, `key` base64 32 bytes}, full `state`); `state` (changed members); `done` (`id`, optional `error`); `list` (`id`, `what`, `items`, `more`); `pong` (`n`); `error` (`code`, `about`); `revoked`. Source: `D/research/phone-remote.md:245-253`.
- State members: `power` (`on`|`standby`), `fg` (webOS id of the app holding keyboard focus; `com.beb.plxnative` is Marquee), `ime` (`{active, owner: app|lumatv, purpose 0-12, hint bits 0x8 lower 0x10 upper 0x20 title 0x40 hidden 0x80 sensitive, enter 0-7, max, text}`), `volume` (`{via: receiver|tv, level, max, muted}`), `acts` (names usable now). Source: `D/research/phone-remote.md:255-265`.
- Actions `act.do`: `home`, `quick`, `settings`, `notifications`, `input`, `pictureoff`, `cameras`, `camera`, `camera-close`, `guide`, `tune`, `launch`, `volume`, `power`. `camera` is not implemented (refused `unavailable`). Source: `D/research/phone-remote.md:172-187`; `D/plugins/phone-remote.md:46`.
- Key names and Linux codes the TV delivers: `up` 103, `down` 108, `left` 105, `right` 106, `ok` 28, `back` 412, `home` 773, `exit` 174, `menu` 139, `info` 358, `guide` 362, `list` 787, `more` 994, `input` 241, `power` 116, `volup` 115, `voldown` 114, `mute` 113, `chup` 402, `chdown` 403, digits `0` 11 and `1`-`9` 2-10, `red` 398, `green` 399, `yellow` 400, `blue` 401, `play` 207, `pause` 119, `playpause` 164, `stop` 128, `rew` 168, `ff` 208, `netflix` 1037, `amazon` 1038. Source: `D/research/phone-remote.md:270-279`.
- Error codes: `bad-message`, `bad-key`, `bad-action`, `too-long`, `no-field`, `off`, `standby`, `not-found`, `unavailable`, `rate`. Source: `D/research/phone-remote.md:281-283`.
- Pointer datagram (UDP, same address and port): 12-byte clear header `4C 52` (`LR`), version 1, kind (1 pointer, 2 ping, 3 pong), session u32, sequence u32 (from 1, per direction); body ChaCha20-Poly1305 with `udp.key`, nonce `4C 52 D 00` + sequence as u64 (D 0 phone to TV, 1 TV to phone), AD = header. Source: `D/research/phone-remote.md:287-298`; `helper/remote/src/datagram.rs:8-30`.
- Pointer plaintext, 24 bytes: x i32, y i32 (running total of motion, 1/16 TV pixel), scroll x i32, scroll y i32 (running totals, 1/16 px), buttons held (bit0 left, bit1 right), left presses u8, right presses u8, centre count u8, flags (bit0 engaged, bit1 scrolling), 3 zero bytes. The TV applies differences with wrapping subtraction: centre steps, motion (at most 4,096 px per datagram), scroll, buttons. Source: `D/research/phone-remote.md:300-318`; `helper/remote/src/datagram.rs:30`.
- Ping plaintext 12 bytes (`id` u32, phone time u64 us); pong 16 bytes (`id`, echoed time, `hold` u32 us). Source: `D/research/phone-remote.md:320`.
- Latency-relevant: phone sends at most 120 pointer datagrams per second while moving; one at once on any button, centre or flag change, with copies at +5 ms and +20 ms (button changes triple-sent); one every 250 ms while engaged or a button held. Source: `D/research/phone-remote.md:86-87,322-323`; `LumaRemoteKit/Sources/LumaRemoteCore/Link.swift:466-471`.
- Latency-relevant: air mouse samples device motion at 100 Hz on its own queue and sends straight from that queue; gain 2,750 px/rad with acceleration curve, One Euro filter, dead zone near 0.01 rad/s. Source: `D/research/phone-remote.md:356-358`; `LumaRemoteKit/Sources/LumaRemoteKit/Input.swift:42-46`.
- Timing and limits: phone sends a frame at least every 2 s (kit pings after 1.5 s idle, `Link.swift:123`); the TV ends a session silent on both channels for 6 s (releases held keys, hides the pointer); key held `down` for 30 s is released; per session 60 frames/s and 250 datagrams/s, beyond that datagrams dropped and frames answered `rate`; 4 sessions at once. Source: `D/research/phone-remote.md:327-332`.
- Reconnect: the link reconnects with backoff, resets backoff after a session of at least 6 s; reports `connecting`, `offline`, `incompatible`. Source: `LumaRemoteKit/CHANGELOG.md` (Unreleased, 1.0.3); `Link.swift:70,254-259`.
- Wake: Active Standby wakes through the `power` key (`power/powerOn {"reason":"remoteKey"}`); deep standby via Wake-on-LAN to the TV's MAC (needs LG's wake-on-network setting; iOS unicast fallback is untested). Source: `D/research/phone-remote.md:113-121`.
- Compositor-side verbs: `phone session on|off`, `phone text BASE64`, `phone edit OP [N]`, `pointer X Y`, `click tap|press|release`, `wheel up|down`, `remote CODE tap|press|release`; state read with `keys`, `ime`, `pointer`. Source: `D/plugins/phone-remote.md:48-52`.
- TV pointer behaviour: absolute pointer on the 1920x1080 scene; vertical scroll turns the wheel one step per 48 px; horizontal scroll ignored; left button clicks, right button is Back; clearing `engaged` hides the pointer. Source: `D/plugins/phone-remote.md:41-43`.
- Version rules: unknown JSON members ignored within version 1; unknown `t`, key, action get `bad-message`, `bad-key`, `bad-action`; a TV that does not speak the version closes without answering. Source: `D/research/phone-remote.md:336-338`.
- Test vectors: `helper/remote/tests/vectors.json` is copied verbatim into `LumaRemoteKit/Tests/LumaRemoteCoreTests/vectors.json` (630 lines); CI fails when they drift. Rust test client `lumaremote` (`discover`, `pair`, `key`, `text`, `act`, `get`, `move`, `scroll`, `bench`, `fake-tv`, `vectors`). Source: `D/research/phone-remote.md:340-344,384-388`; `LumaRemoteKit/README.md` ("Tests").

## 1.4 Reusable for a browser remote, and what is Plex-specific

Reusable almost unchanged:
- The wire protocol and the whole phone-side core: pairing, Noise session, frames, datagram codec, Bonjour discovery, link with reconnect and keepalive, Keychain store, Wake-on-LAN (`LumaRemoteCore`, 8 files). Marquee-free (the only Marquee reference is the constant `marqueeApp = "com.beb.plxnative"`, `Messages.swift:399`). Source: `LumaRemoteKit/Package.swift`; `Messages.swift:399`; `D/research/phone-remote.md:418-423`.
- The TV side engine crate `lumaremote` (`helper/remote`): no LumaTV dependencies by design. Source: `D/plugins/phone-remote.md:7-9`; `D/research/phone-remote.md:151-153`.
- The pointer/scroll model (running totals in UDP datagrams, absolute pointer at 1920x1080, wheel steps), trackpad and air-mouse input code (`Input.swift`, `Touchpad.swift`, `Pointer.swift`), keyboard bridge driven by an `ime` state, D-pad and key views, `PairingView`, `TVPicker`, `DiagnosticsView`, theming through `RemoteTheme`. Source: files above.
- `LumaRemoteFakeTV` and `vectors.json` for tests without a TV. Source: `LumaRemoteKit/README.md` (table, "Tests").
- Pairing UX pattern: physical-remote OK gate on the TV, code plus QR, per-device revocable keys, plugin off by default with consent text. Source: `D/plugins/phone-remote.md:3-16`.

Must change for a browser:
- The listener: the current server lives in the LumaTV helper and injects into the LumaTV compositor, not into a browser. For a browser, the same protocol would terminate on the server side next to Chromium (Chromium input events via CDP or similar; Not found in these repos) or on the TV app; the helper's `server.rs` can be reused as engine only if it is given another sink than `phone ...` compositor verbs. Source: `D/plugins/phone-remote.md:48-52`.
- Key set: protocol keys are TV remote keys with Linux codes; a browser needs pointer, wheel, tab and URL operations, which are not in `act.do` (`home`, `quick`, `settings`, `notifications`, `input`, `pictureoff`, `cameras`, `camera`, `camera-close`, `guide`, `tune`, `launch`, `volume`, `power`) and not in `get` (`apps`, `channels`, `cameras`). Tabs, URL entry, bookmarks: Not found in the protocol. Source: `D/research/phone-remote.md:172-187,239`.
- Text entry: `text` goes into the field the compositor tracks as a text model (`ime`); a browser needs its own focused-field reporting. Source: `D/research/phone-remote.md:58-65`.

Plex- or LumaTV-specific:
- `fg` `com.beb.plxnative` and the Marquee-first key group; LumaTV actions (`quick`, `settings`, `notifications`, `pictureoff`, `cameras`, `tune`, `launch`, `volume` via the AV receiver plugin); `accent` from LumaTV's theme; Active-Standby wake path. Source: `D/research/phone-remote.md:172-187,247,258`; `UI/LumaRemoteView.swift:334`.
- `marquee-ios/App/Remote/TVRemote.swift` (mini bar, Home button, Settings integration) and `docs/DESIGN.md` §8.9 gestures belong to the Marquee app. Source: those files.
- Marquee's webOS app mocks and CSS (`Marquee/docs/marquee/mocks/`) are Lucent v2 TV-UI tokens for Marquee screens; they carry no phone remote. Source: `marquee.css:1-12`.

# 2. Hardware video in the current LumaBrowser (upstream WebOS-Chromium)

## 2.1 Overview and file map

- The app is Chromium 151 (webOS-ports/chromium151 plus patches) running natively on the TV; the app's `bin/run` is the C launcher `cnrun`, which starts `bin/run.sh` (which execs `browser/chrome`) as a child and stays its parent as the hardware video service. Source: `L:1-2`; `source/README.md`; `source/package/appinfo.json.in` (`"main": "bin/run"`); `source/package/run.sh:1-4`.
- Patches that make up hardware video: `0023` renderer (`content/renderer/media/cn_ndl_renderer.{cc,h}`, 684-line patch), `0024` viz hole, `0025` video window (ozone), `0026` RGBA output, `0039` old-NDL gate, `0040` NOHW fallback, `0048` old-NDL pacing, `0049` playstate file, `0055` HEVC type check. Source: `P/INDEX.md` (rows 0023-0026, 0039, 0040, 0048, 0049, 0055).
- Hardware video exists only when the launcher found LG's library and bound the socket; otherwise `CN_MEDIA_SOCK` is unset and Chromium uses its normal renderer. Source: `L:938-947`; `P/0023-webos-hwvideo-renderer.patch:5`; renderer `CnNdlRendererFactory::Enabled()` (`P/0023...:578`).
- Packaging: `mkipk.py` installs the launcher as `bin/run` and `run.sh` as `bin/run.sh` ("luna-service2 lets only the role's exe (bin/run) use the app's media bus names"). Source: `source/package/mkipk.py:160-163`.

## 2.2 Why only the app's main binary may drive the decoder

- luna-service2 grants the app's bus names (`com.webos.media.client.*`) only to the executable named in the app's role, which is `bin/run`. A shell script there appears as `/bin/sh`, and Chrome's exe is `browser/chrome`, so neither may talk to LG's media server. The launcher can, so it calls NDL DirectMedia. Source: `L:1-7`.
- `libNDL_directmedia.so.1` is `dlopen`ed (types from webosbrew/webos-userland); nothing from LG's firmware is included in the repo. Source: `L:22-23,111-113`; `source/README.md`.
- `APPID` must be set: NDL registers its pipeline with `$APPID`; without it the pipeline had appId "" and LG's media policy kept the picture muted (sound played). The launcher does `setenv("APPID", app_id, 1)`. Source: `L:931-935`.

## 2.3 The media socket protocol (`CN_MEDIA_SOCK`)

Transport:
- Unix stream socket at `/tmp/<appid>/media.sock`, created by the launcher (`bind`, `listen(ls, 8)`, non-blocking, `SOCK_CLOEXEC`), exported to Chrome as env `CN_MEDIA_SOCK`. Up to `MAXC 16` clients. Source: `L:936-947,392-393`.
- Several clients connect: each renderer process connects per `CnNdlRenderer` (the renderer sets `SO_SNDBUF` 4 MB); the browser process connects once for WINID/GEOM. Source: `P/0023...:255-270`; `P/0025-webos-hwvideo-video-window.patch:84-90`.

Framing:
- One message = `struct cn_hdr { uint32_t type, len; }` followed by `len` payload bytes; host byte order (little-endian ARM). `len` over 64 MiB drops the client. The reader accumulates and parses whole messages. Source: `L:9,48,399-420`.
- Enum: `CN_OPEN=1, CN_VIDEO=2, CN_AUDIO=3, CN_CLOSE=4, CN_GEOM=5, CN_SRC=6, CN_WINID=7, CN_VSIZE=8, CN_NOHW=9`. Source: `L:47`.

Messages:
- `OPEN` (renderer to launcher): `struct cn_open { uint64_t token[2]; int32_t codec, width, height, audio_rate, audio_channels; }` (36 bytes). `codec`: 1 H.264, 2 HEVC, 3 VP9, 4 AV1. `audio_rate` 0 means video only; `audio_channels` always 2. `token` is the renderer's `UnguessableToken` (high, low). The launcher unloads any current stream and loads the new one. Source: `L:10,49,304-342`; `P/0023...:75-90,357-366`.
- `VIDEO` (renderer to launcher): payload `int64 pts_ms` + one access unit; goes to `NDL_DirectVideoPlay(data, size, pts)` (API 2) or `NDL_DirectVideoPlayWithCallback` (API 1, pts not used by NDL). Source: `L:11,349-358`; `P/0023...:319-355`.
- `AUDIO` (renderer to launcher): payload `int64 pts_ms` + interleaved S16LE stereo PCM; goes to `NDL_DirectAudioPlay`. Source: `L:12,349-358`; `P/0023...:SendAudio`.
- `CLOSE` (renderer): payload the 16-byte token; the launcher unloads only if it equals the current stream's token. Source: `L:13,372-374`.
- `GEOM` (browser, via viz hole report): `struct cn_geom { uint64_t token[2]; int32_t x, y, w, h; }` (32 bytes; the browser sends token 0,0); video rect in window pixels; the launcher stores it and (API 1) calls `NDL_DirectVideoSetArea(x,y,w,h)`; on API 2 with no browser window id it calls `place_video()`. Source: `L:14,50,375-390`; `P/0025...:141-200`.
- `SRC` (renderer): `struct Src { uint64_t token[2]; int32_t w, h; }` sent when the stream's natural size changes without a codec change. The launcher's `on_msg` has no `case CN_SRC`; the message is ignored. Source: `P/0023...:75-77,394-410`; `L:343-390` (switch cases: OPEN, VIDEO, AUDIO, WINID, CLOSE, GEOM).
- `WINID` (browser to launcher): payload = the window id string Chrome exported from its own window surface (no NUL, up to 127 bytes); the launcher remembers the fd as `winid_fd`. Used for `NDL_DirectMediaSetWindowId`. Source: `L:15-16,366-371`; `P/0025...:84-93`.
- `VSIZE` (launcher to browser on the WINID connection): `uint32 type=8, len=8, w, h` (16 bytes), sent on every OPEN when the browser exported the window; the browser sets the plane's source region from it. Source: `L:17,336-340`; `P/0025...:145-153`.
- `NOHW` (launcher to renderer): zero length. Sent when an NDL API 1 call fails or when the codec/rate is refused; the renderer that is playing reports `PIPELINE_ERROR_DECODE` so the page's player can reload, later renderers use `RendererImpl`. Source: `L:18,233-243,308-312`; `P/0040-webos-hwvideo-nohw-software-fallback.patch:1-2`.
- `pts_ms` is the renderer's presentation time in ms since its OPEN: `PtsMs(ts) = (now - open_wall) + (ts - MediaTime())`, clamped at 0. Source: `L:19`; `P/0023...:314-317`.

What Chromium sends and when (`CnNdlRenderer`, a `media::Renderer` that wraps the normal renderer as fallback):
- Used only if video exists, the codec is one of H.264/HEVC/VP9/AV1, it is not encrypted, and (if audio exists) audio is unencrypted with a sample rate in {48000, 44100, 32000, 24000, 16000, 12000, 8000, 22050}. Audio-only, encrypted (EME) and other codecs use `RendererImpl`. Source: `P/0023...:79-96,242-252`.
- Video packets: access units from the demuxer (`DecoderBuffer` bytes), with `EnableBitstreamConverter()` on the video stream so FFmpeg's H.264/HEVC come as Annex B (MSE already is). The bytes for VP9 and AV1 are the demuxer's buffers as is; no further conversion code exists in the patch. Source: `P/0023...:124`.
- Audio: Chromium decodes audio itself to float PCM (Opus with `OpusAudioDecoder`, other codecs with `FFmpegAudioDecoder`), downmixes more than 2 channels to stereo (centre and rest at -3 dB), applies the page volume, converts to S16LE and sends. NDL gets PCM only. Source: `P/0023...:127-137,SendAudio`.
- Flush (seek, pause-flush): `SendClose()`, clears queues, bumps a generation counter. `StartPlayingFrom(t)`: `SendOpen()` then starts requesting video; so a seek is CLOSE then OPEN then new data. Source: `P/0023...:164-200`.
- Codec change in the stream (`kConfigChanged`): new `OPEN`; size-only change: `SRC`. Source: `P/0023...:394-410`.
- Pacing: a 10 ms timer calls `Pump()`; a video frame is sent when `pts - media_time <= lead` (lead default 150 ms, env `CN_NDL_LEAD_MS`); audio buffers likewise; media time = wall clock while playing, never more than 300 ms past the last video timestamp sent. Source: `P/0023...:104,305-312,523-545`.
- Pause: `SetPlaybackRate(rate)` only sets `playing_ = rate > 0` and rebases the clock; nothing is sent to the launcher on pause, only the data stops (a new OPEN follows a Flush). Rates other than 1 are not applied (the clock runs at wall speed). Source: `P/0023...:SetPlaybackRate, MediaTime`.
- Volume: applied by scaling PCM in the renderer; not sent to NDL. Source: `P/0023...:SetVolume, SendAudio`.
- End of stream: the renderer calls `OnEnded()` itself when both streams are drained and media time reached the last timestamp. Source: `P/0023...:Pump`.
- Buffering state is reported by the renderer (`BUFFERING_HAVE_ENOUGH` after the first video frame is sent and audio is queued). Source: `P/0023...:Pump`.
- Video holes: the renderer paints a `VideoHoleFrame` (token, natural size) into the compositor sink. Source: `P/0023...:299-301`.

What comes back: only `VSIZE` (browser connection) and `NOHW` (renderer connection). There is no acknowledgement, no playback position, no buffer level and no error report on any other message; the launcher logs to `/tmp/<appid>/media.log` (first failures, frame count every 1500 frames with `NDL_DirectVideoGetRenderBufferLength`). Source: `L:343-390,352-357`.

Launcher behaviour per client: `stream_open` closes the current stream first; messages for a stream are accepted only from the client that opened it (`cur_owner`); a client that disconnects closes its stream. A stream with no audio gets a block of 1,600 stereo silence samples per video frame (`silence[1600*2]`). Source: `L:336-358,393-398`.

## 2.4 How the launcher drives LG's decoder

New API (NDL API 2, webOS 5+; detected by `NDL_DirectMediaLoad` being present):
- Symbols: `NDL_DirectMediaInit`, `SetWindowId`, `Load`, `Unload`, `Quit`, `NDL_DirectVideoPlay`, `NDL_DirectAudioPlay`, `NDL_DirectMediaGetError`, optional `NDL_DirectVideoGetRenderBufferLength`, `NDL_DirectMediaSetAppState`, `NDL_DirectVideoSetArea`. Source: `L:111-130`.
- Order that works on webOS 10: `SetWindowId(window)` BEFORE `Init(appId)`, then `Load` with video and audio info. Source: `L:22-23,324-326`.
- `NDL_DATA_INFO`: `video {width, height, type}`, `audio.pcm {type 1, format "S16LE", layout "interleaved", channelMode "stereo", sampleRate code}`. Sample rate codes API 2: 48000=1, 44100=2, 32000=3, 24000=4, 16000=5, 12000=6, 8000=7, 22050=8; unknown rates fall back to code 1. Source: `L:52-58,321-331`.
- Codec enum passed straight from `cn_open.codec` (1 H.264, 2 HEVC, 3 VP9, 4 AV1). Source: `L:326`; `P/0023...:79-86`.
- Profiles and levels: the renderer checks only the codec, not the profile. HEVC is declared supported (for `canPlayType`/`isTypeSupported`) only for Main and Main 10, only when `CN_MEDIA_SOCK` is set, and never when `CN_NDL_API=old`. Profile limits for H.264, VP9, AV1: Not found. Source: `P/0055-webos-hwvideo-hevc-type-check.patch:1-6,26-36`.
- Resolution and fps: the launcher enforces no limit. The limits are set in the TV Tools extension: "Auto" = any codec up to 1080p60 with hardware decoding (memory limit), H.264 up to 1080p30 on webOS 4, 720p30 in software; `maxRes` option 2160 is opt-in and "can stutter when a video starts". A 4K HEVC file played on an LG C1 with 0 dropped frames (patch 0055 header). Source: `source/package/ext/tvtools/settings.js:10-12,40-51`; `README.md:36-37,70,78-79`; `P/0055...:4-5`.
- Measured: YouTube AV1 1080p60 0 dropped of 3,914 frames and of 9,330 frames; YouTube TV interface 1080p60 0 dropped of 5,299. Source: `README.md:228-229,241-242`.
- Video plane placement: see 2.5. Audio: NDL plays the PCM through its own pipeline (the launcher's PCM goes to `NDL_DirectAudioPlay`); other page audio (WebAudio, WebRTC) goes to the system PulseAudio (`PULSE_SERVER=unix:/var/run/pulse/native`). Source: `L:12`; `source/package/run.sh:280-285`.
- `NDL_DirectMediaSetAppState` is looked up but never called in the launcher. Source: `L:130,131` and `grep` of `cnrun.c`.
- Unload: `stream_close` calls `NDL_DirectMediaUnload` then `NDL_DirectMediaQuit`. Source: `L` function `stream_close`.

Old API (NDL API 1, webOS 4; used when `NDL_DirectMediaLoad` is absent):
- Symbols all required (else hardware video off): `NDL_DirectMediaInit(appId, cb)`, `NDL_DirectMediaQuit`, `NDL_DirectMediaGetError`, `NDL_DirectVideoOpen`, `NDL_DirectVideoClose`, `NDL_DirectVideoSetCallback`, `NDL_DirectVideoPlayWithCallback`, `NDL_DirectVideoSetArea`, `NDL_DirectAudioOpen`, `NDL_DirectAudioClose`, `NDL_DirectAudioPlay`. Source: `L:100-110`.
- Only H.264 (`NDL_DIRECTVIDEO_DATA_INFO_T { width, height, source=1 }`); other codecs: `NOHW`. Chromium also gates this in the renderer (patch 0039: `OldNdlApi()` keeps non-H.264 in software and exports no video window). Source: `L:60,272-279`; `P/0039-webos-hwvideo-old-ndl-gate.patch:1-2,18-24`.
- Audio: `NDL_DIRECTAUDIO_DATA_INFO_T { number_of_channel 2, bit_per_sample 16, no_delay_mode 1, no_delay_upper_time 48, no_delay_lower_time 16, channel 0, source 1 (PCM), frequency }`. Frequency codes API 1: 8k=2, 12k=4, 16k=5, 22.05k=6, 24k=7, 32k=8, 44.1k=9, 48k=10; other rates refused (`NOHW`). Source: `L:60-65,256-270,281-296`.
- Placement: `NDL_DirectVideoSetArea(x, y, w, h)` at open (full 1920x1080 until the first GEOM) and on each GEOM change. No window id, no `Load`, no pts. Source: `L:272-300,375-390`.
- Any failed call: `old_fail` sends `NOHW`, closes the stream, and (for a play/open failure) writes `bad` to `/tmp/<appid>/hw.state`; later OPENs in the session get `NOHW`; the next start tries hardware again (`hw.state` renamed to `hw.state.prev`). `run.sh` writes `hw.json` `{"hardware": ..., "h264": true}` for TV Tools. Source: `L:233-255,955-965`; `source/package/run.sh:240-262`.
- Pacing differs (patch 0048): the old decoder shows frames as they arrive in decode order, so the renderer sends frame k at `base + k * frame_duration` (clamped to `pts - 6 frames .. pts`, base starts 2 frames before the first pts, frame duration = smallest step among the last 16 timestamps within 8-100 ms); API 2 keeps the display-time gate. Source: `P/0048-webos-hwvideo-old-ndl-decode-order-pacing.patch:1-4,19-60`.
- HEVC is not offered on webOS 4. Source: `P/0055...:5-6`.
- Launcher exports `CN_NDL_API=new|old|none` before Chrome starts. Source: `L:954-955`.

## 2.8 What a network version could reuse almost unchanged

- `source/package/launcher/cnrun.c` (1,096 lines): the NDL layer (`ndl_open_lib`, `ndl_open_old`, `stream_open`, `stream_open_old`, `stream_close`, `old_play`, `api1_rate`, `old_fail`), the Wayland export/placement code (`wayland_up`, `place_video`, `probe_set_property`), the screen-saver guard, the signal handling, the glibc-2.17 build (`build.sh`, zig, softfp ARM) and the `tv_too_old` check.
